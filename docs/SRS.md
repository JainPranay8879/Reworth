# Software Requirements Specification (SRS) — ReWorth
Version 1.0 · Course: Mini Project – I (Real-World Application Development)

## 1. Introduction
**Purpose.** This document specifies the requirements of ReWorth, a web application that helps a person decide whether an old or damaged product should be **Repaired, Reused, Donated, Recycled or Replaced**.
**Scope.** A Flask + SQLite web application with a transparent rule-based decision engine, user accounts, assessment history and an administrator area. Out of scope: payments, repair booking, live market prices, technician diagnosis, image analysis, machine learning.
**Definitions.** *Assessment* – one evaluation of one product. *Engine* – the rule-based scoring module. *Diagnosis Required* – a result returned when information is too uncertain for a confident recommendation.

## 2. Overall description
**Stakeholders.** Consumers/students (primary), registered users, administrator (project owner/faculty demo), evaluators.
**User classes.** Guest (can assess, nothing saved) · Registered user (history, account) · Administrator (user and assessment oversight).
**Operating environment.** Python 3.12, any modern browser, SQLite; deployable on Render via gunicorn.
**Constraints.** Free-tier hosting (ephemeral disk unless a disk is attached); no third-party paid APIs; recommendations are advisory, not a technical diagnosis.
**Assumptions.** Users know approximate age/condition; costs are optional and never invented by the system.

## 3. Functional requirements
Priority: **M** must · **S** should · **C** could.

| ID | Requirement | Pri |
|---|---|---|
| FR-01 | A guest shall be able to complete a multi-step product assessment without an account. | M |
| FR-02 | The system shall validate inputs (required fields, age 0–100, non-negative costs, replacement cost > 0, valid category, text-length limits) and return clear errors. | M |
| FR-03 | The engine shall return one of Repair / Reuse / Donate / Recycle / Replace / Diagnosis Required, with score (0–100), confidence, information-quality %, factor breakdown, explanation and next step. | M |
| FR-04 | Costs are optional; when absent the engine shall not assume a price. | M |
| FR-05 | A visitor shall be able to register with name, unique email and password (min 8 characters). | M |
| FR-06 | A registered user shall be able to log in and out; passwords shall be stored hashed. | M |
| FR-07 | Assessments made while logged in shall be saved and shown on the user's dashboard with decision counts. | M |
| FR-08 | A user shall be able to edit name/email, change password (needs current password), export own history as CSV, and delete the account (needs password). | S |
| FR-09 | A user who forgot a password shall be able to recover access through a single-use, 30-minute reset link (email, or generated by an administrator). | S |
| FR-10 | An administrator shall be able to log in via a separate admin page. | M |
| FR-11 | An administrator shall be able to view usage statistics, filter/search all assessments and export them as CSV. | S |
| FR-12 | An administrator shall be able to list users, change roles, and generate a password-reset link. | S |
| FR-13 | The system shall expose `GET /health` for monitoring. | S |
| FR-14 | The system shall migrate an older database to the current schema automatically. | C |

## 4. Non-functional requirements
| ID | Requirement |
|---|---|
| NFR-01 Security | CSRF tokens on every state-changing request; hashed passwords; server-side role checks; login throttling (5 failures / 15 min); secure, HttpOnly, SameSite cookies; security headers; CSV formula-injection protection; parameterised SQL; auto-escaped templates. |
| NFR-02 Performance | Pages and API respond in < 1 s (p95) at 20 concurrent users on the target hosting. |
| NFR-03 Usability | Responsive layout (≥ 360 px), step-by-step form, plain-language explanations. |
| NFR-04 Reliability | Errors return friendly pages/JSON; invalid input never crashes the server. |
| NFR-05 Maintainability | Single-module Flask app, automated tests (31), CI on every push. |
| NFR-06 Portability | Runs locally with `python app.py`; deploys with one `render.yaml`. |
| NFR-07 Privacy | Only name, email and the user's own assessments are stored; users can delete their account and data. |
| NFR-08 Explainability | Every recommendation shows the factors behind it. |
